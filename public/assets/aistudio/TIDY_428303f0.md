# TIDY: keeping code, folders and data in order

Companion to `SKILL.md`. Read it when the task is cleaning or filtering code, removing dead or duplicate code, restructuring folders and files, naming things, tidying a database schema or content data, or when starting any multi-file project, so that it starts tidy. The requirement lock, the lean ladder and the reply style of `SKILL.md` still apply.

The goal of every rule here: **a person looking for something finds it on the first guess, and nothing in the project is there without a reason.**

**Contents:** 1 Principles (Y) · 2 What you need first · 3 Commands · 4 The procedure · 5 Code clean-up · 6 Folders and files · 7 Database · 8 Content data · 9 Report formats · 10 QA gate

---

## 1. Principles (Y)

- **Y1 Behavior stays the same.** Tidying changes where things live and how they read, never what the app does. A bug you notice is reported, not silently fixed in the middle of a tidy: mixing a clean-up with a behavior change makes both impossible to review.
- **Y2 Evidence before deletion.** "Unused" has to be shown: say where you looked and found no reference (5.2). When the evidence is weak, **quarantine** instead of deleting (move to `_trash/` with the date) and say so. Deleting needs the user's yes.
- **Y3 Small, reversible steps.** Each step leaves the project working and could be committed alone. Make a checkpoint first: a git commit or branch, or a zip copy when there is no git.
- **Y4 The project's conventions win.** Inherit its naming, formatter and structure style. Introduce a convention only where none exists, and say which one you chose.
- **Y5 One obvious home per kind of thing,** and names that say what is inside. `PROJECT_MAP.md` records where things live.
- **Y6 Lean applies to structure too.** No layers, folders or abstractions "for later". A folder with one file is noise; flatten it.
- **Y7 Data is more dangerous than code.** No destructive database operation without a backup, a tested migration, a rollback and the user's yes. Never on production straight from a chat suggestion.
- **Y8 Scope is sovereign.** Tidy what was named. Other mess you notice goes in a list (`DEBT.md`); you do not wander into it.

## 2. What you need before you start

**Chat-only:** you cannot see the project, so ask once, in one message, for what the task needs:

1. **The file tree.** Best: `git ls-files` (tracked files only). Otherwise `tree -a -I "node_modules|.git|dist|build" -L 4`; on Windows `tree /F /A`, with `node_modules` cut out.
2. **The manifest:** `package.json`, `pubspec.yaml`, `requirements.txt` or the equivalent.
3. **For database work:** the schema as it really is (`pg_dump --schema-only`, `schema.prisma`, the migrations folder, a Supabase or Firebase export, or the code that reads and writes each collection), plus row counts if they can get them.
4. **The 2-5 files they find messiest,** and what must not be touched.

Do not invent a tree or a schema you have not been shown. Plan from what you were given and mark the rest "chưa thấy".

**Agent mode:** gather these yourself. List the files, read the manifest, search for references, and run the build, the tests and the linter **first**, so there is a baseline to compare against. Check that the working tree is clean, or ask.

## 4. The procedure (every tidy command)

1. **Baseline.** What works now, and how you know (build, tests, how to run it). Make the checkpoint.
2. **Inventory.** List what is in scope.
3. **Classify** each item, with evidence: `keep` · `rename` · `move` · `merge` · `split` · `delete` · `quarantine`.
4. **Plan.** The target state, the move map and the ordered steps. Mark the steps that need the user's decision.
5. **Approve.** Show the plan and wait for yes whenever it deletes something, renames something public, moves many files or touches data. A single-file tidy that removes only proven-dead code may proceed and report.
6. **Execute in order.** After each step, update every reference, then run the build and tests (agent) or say exactly what to run (chat).
7. **Verify.** Same behavior, no reference to an old path or name, the app starts.
8. **Document.** Update `PROJECT_MAP.md`; list what was left in `DEBT.md`.

## 5. Code clean-up

### 5.1 What to look for

| Kind | Examples | Action |
|---|---|---|
| **Dead code** | unused imports, variables, functions, components, CSS selectors, routes, files, assets, dependencies; flags that are always on or off; unreachable branches | Remove, with evidence (5.2). |
| **Leftovers** | commented-out code, `console.log` and debug prints, TODOs with no owner, sample data in production paths, files named `final2`, `copy`, `old`, `backup`, `test1` | Remove, or quarantine if unsure. Git already keeps history. |
| **Duplication** | the same logic in three or more places | Extract once. Two places: leave them unless they must change together. |
| **Names that lie or say nothing** | `data`, `temp`, `handleClick2`, `utils2`, `newFile`; mixed languages or styles in identifiers | Rename to what the thing is. One language and one style for identifiers, the project's own. |
| **Wrong size or shape** | a file over about 300 lines or with more than one job; a function over about 40 lines or nested more than 3 levels; a component that fetches, computes and renders | Split by responsibility; return early; separate data from view. |
| **Magic values** | repeated literals: colors, sizes, durations, URLs, storage keys, point values | Tokens or constants, in one place. |
| **State sprawl** | duplicated state, state that could be derived, globals, values passed down through more than 3 levels | Derive it, lift it or colocate it. |
| **Silent failure** | empty `catch` blocks, unhandled promises, missing loading and error states | Handle it or report it. Progress is never lost silently. |
| **Security and privacy** (report first, at the top) | API keys or secrets in code or in git history; student personal data in logs or stored in the clear; endpoints with no permission check; `innerHTML` fed with content | Tell the user at once. A leaked key must be rotated, not only deleted. |
| **CSS** | unused selectors, duplicated rules, hard-coded colors and sizes, `!important` chains, z-index wars, deep selectors | Tokens, flat selectors, one z-index scale. |
| **Assets** | unused, duplicated, oversized (an image over about 300 KB), unclear names (`image1.png`, `Screenshot 2024….png`) | Remove, compress, rename (6.2). |
| **Dependencies** | unused; two libraries for one job; heavy for a small use; unpinned | Remove, merge, replace by the platform, pin. |

### 5.2 Proving "unused"
A thing is unused only when **all** of these come back empty:

- a text search for its name across the whole repository, including tests, configuration, HTML, CSS `url()`, JSON, content files and documentation;
- dynamic references: names built from strings, dynamic `import()`, file-based routes (`pages/`, `app/`), framework conventions (`public/`, auto-imports, Flutter assets in `pubspec.yaml`, Android and iOS resource names), switches driven by environment variables;
- outside users: a public endpoint, a deep link, a database column another service reads, an asset referenced from content data.

If any of these is uncertain, quarantine or keep, and say why. In agent mode, tools give evidence faster when the project has them or the user agrees to run them: the linter's unused rules, TypeScript's `noUnusedLocals`, an unused-file and unused-dependency finder such as `knip`, `flutter analyze`. A tool's output is evidence to check, not a verdict.

### 5.3 Order of operations (safest first)
Formatting only, as its own step → remove proven-dead code → rename → extract duplicates → split files → move files. **Never mix a formatter run with logic edits in one step:** it buries the real change in noise.

### 5.4 The `lean` pass
Walk the named code with the ladder from `SKILL.md` 7.1 and list every replacement found:

```
- custom modal + focus-trap library (86 dòng, 1 thư viện) → <dialog> (12 dòng, 0 thư viện)
- formatScore() tự viết → Intl.NumberFormat('vi-VN')
- wrapper useStorage quanh một lần gọi localStorage → gọi thẳng trong try/catch
- thư mục helpers/ có 1 file 1 hàm → chuyển hàm vào feature dùng nó
```

Report lines, files and dependencies removed. Never cut what `SKILL.md` 7.1 says is never cut: validation at trust boundaries, error and data-loss handling, security, accessibility, required states, the child-safety lines, subject correctness.

### 5.5 Comments and documents
Delete comments that restate the code. Keep the ones that say *why*. One README that explains how to run the project in five lines. No decorative file headers.

## 6. Folders and files

### 6.1 Principles
- **Feature first.** Once a project has more than a handful of files, group by what the product does (lesson, quiz, progress, a game, a simulation), not by file type. A feature folder holds its UI, logic, styles and tests together: one place to look, one folder to delete.
- **Shared things are promoted late.** Something moves to `components/` or `lib/` only when a second feature needs it.
- **Dependencies point one way:** app or routes → features → shared (components, lib). Features never import each other's internals. Shared code never imports a feature.
- **Content is not code.** Lessons, questions, translations and lesson images live in `content/` or in the database, never inside components (`SKILL.md` E9).
- **One home per kind of thing.** Tokens in one file. Backend calls in one layer. Storage keys in one module.
- **Shallow.** At most 4 levels below `src/`. Flatten a folder with one file; split a folder with more than about 12.
- **Generated and secret files stay out of source control:** `node_modules/`, `dist/`, `build/`, `.env`, listed in `.gitignore`.

### 6.2 Naming
- **Files and folders:** `kebab-case` for web files (`question-card.js`), except where the framework dictates otherwise (React components `QuestionCard.tsx`, Dart `question_card.dart`). One style per kind, across the project.
- **Name by content, not by history:** no `new`, `final`, `v2`, `copy`, `temp`, `test1`, and no dates in names.
- **Specific and searchable:** `quiz-scoring.js`, not `helpers.js`. No `utils/` dumping ground: name the job (`format-number.js`, `storage.js`).
- **Tests sit next to the code:** `quiz-scoring.test.js`.
- **Assets:** `<feature>-<what>-<variant>.<ext>`, lower case, no spaces, no Vietnamese marks in file names (`lesson-ucln-diagram.svg`): marks and spaces break URLs and tools on some systems.
- **Identifiers:** one language. Booleans start with `is`, `has` or `can`. Functions are verbs, components are nouns, handlers are `on…` or `handle…`. `UPPER_SNAKE` only for true constants.

### 6.4 Where does it go?

| I have… | It goes in… |
|---|---|
| a design token | `styles/tokens.css` |
| a button, dialog or tag used by two or more features | `components/` |
| a component used on one screen only | that feature's folder |
| a function that formats, validates or calculates, used by two or more features | `lib/<job>.js` |
| a call to the backend | the feature's `api` file |
| a question bank, lesson text | `content/` or the database |
| an icon | the one SVG sprite |
| an image that belongs to the interface | `assets/images/` |
| a storage key, a route name, a point value | the feature's constants |
| a schema change | `db/migrations/<timestamp>_<what>.sql` |
| a decision and its reason | `docs/DECISIONS.md` |
| something knowingly left messy | `docs/DEBT.md` |

### 6.5 Moving files safely
Write the **move map** (old path → new path). Update every reference: imports, HTML `src` and `href`, CSS `url()`, dynamic imports, configuration and test paths, content references, documentation. Use `git mv` so history follows the file. Move one feature at a time and build after each. Leave no re-export shim behind unless the old path is public.

### 6.6 `PROJECT_MAP.md`
The file that makes a project findable. Keep it under about 60 lines and update it in the same change that moves things.

```
# PROJECT MAP
Run:    <how to start it, one or two commands>
Stack:  <framework, language, styling, backend, hosting>

## Where things live
| Looking for…                          | Go to…                         |
|---------------------------------------|--------------------------------|
| colors, type, spacing tokens          | src/styles/tokens.css          |
| shared buttons, dialogs, tags         | src/components/ui/             |
| the quiz screens and logic            | src/features/quiz/             |

## Features
| Feature | Folder | Entry file | Data it reads and writes |

<main entities and how they relate; where the schema lives>

<file naming, identifier language, how to add a feature in five steps>
```

## 7. Database

### 7.1 Safety first (Y7)
- Work from the **real** schema, never from memory of what it probably is.
- Back up or export before any change, and say how to restore.
- Change structure through **migration files**, never by hand in a console.
- Rehearse on a copy with realistic row counts.
- Each destructive step (dropping a column or a table, deleting rows) is separate, comes last, and waits for the user's yes.
- In chat-only mode you write the plan and the scripts; the user runs them.

### 7.2 Inventory and red flags
For each table or collection, record its purpose, row count, columns (type, nullable, default), keys, indexes, and which code reads and writes it. Then flag:

no primary key · no foreign keys · look-alike tables (`users`, `user`, `tbl_user`, `users_new`) · columns no code uses and that are always null · numbers, dates or JSON stored as text · comma-separated lists in one column · the same fact stored in two places · inconsistent names · no timestamps · no index on foreign keys or frequent filters · free-text values that should be a fixed set (`math`, `Math`, `toan`) · orphan rows · test rows in production.

### 7.3 Naming (when the project has no convention)
`snake_case`. Tables plural (`students`, `attempt_answers`). Primary key `id`. Foreign key `<singular>_id`. Timestamps `created_at` and `updated_at`, stored in UTC. Booleans `is_…` or `has_…`. No prefixes (`tbl_`), no abbreviations (`qstn`), no reserved words, no Vietnamese marks, one language.

### 7.4 Modeling rules
- **One fact in one place.** Normalize transactional data.
- Every table has a primary key. Relations are foreign keys, with `ON DELETE` chosen on purpose.
- **Constraints carry the rules:** `NOT NULL`, `UNIQUE`, `CHECK`, fixed value sets. The database is the last line of defense against bad data.
- Index foreign keys and frequent filters. Many-to-many goes through a join table. Lists are rows, not text.
- A JSON column only for a shape that truly varies (a question's `body` and `answer`), never for something you filter or join on.
- **Derive, do not duplicate** (scores, counts, streaks), unless a measured performance need exists. Then name it a cache and keep a way to rebuild it.
- Soft-delete only where history matters (attempts), and filter it in one place.
- Store time in UTC and display it in `Asia/Ho_Chi_Minh`. Points and money are integers.

### 7.5 Document databases (Firestore, MongoDB)
- Shape documents by how screens read them. Collection names plural, one casing style.
- **No unbounded arrays.** A class's members are a subcollection or their own collection, not an array inside the class document.
- Duplicate only small, stable fields, and name the source of truth for each.
- A `schemaVersion` field on documents that will evolve, so they can be migrated.
- **Security rules are part of the schema:** a student reads and writes only their own documents; content is read-only to students; a teacher reaches student data only through class membership. Rules and composite indexes live in the repository.

### 7.6 Vietnamese text
- **Normalize to Unicode NFC when writing.** The same visible text in decomposed form compares as different, which breaks search, uniqueness and joins.
- **For search, store an accent-free lowercase key** next to the original, and never strip marks from the original. `đ` does not decompose, so it needs its own rule:
  ```js
  const searchKey = (text) => text.normalize('NFD').replace(/[̀-ͯ]/g, '').replace(/đ/g, 'd').replace(/Đ/g, 'D').toLowerCase().trim();
  // searchKey('Ước lượng ĐƯỜNG tròn') === 'uoc luong duong tron'
  ```
- **Sort with a Vietnamese collation** (`new Intl.Collator('vi')`, or an ICU `vi` collation in the database). Plain code-point order puts `Đ` and accented names in the wrong place.
- Imported content may arrive in legacy encodings (TCVN3, VNI). Convert it before it enters the database.

### 7.7 A reference model for a learning app
A starting point for a relational database. Adapt it to the product; never impose it on a schema that already works.

| Table | Key columns | Notes |
|---|---|---|
| `profiles` | `id`, `role` (student, teacher, parent, admin), `display_name`, `grade`, `avatar_key` | The minimum about a person. Sign-in data stays with the auth provider. |
| `classes` | `id`, `name`, `grade`, `school_year`, `teacher_id` | |
| `enrollments` | `class_id`, `student_id`, `joined_at` | Key: (`class_id`, `student_id`). |
| `subjects` | `id`, `code`, `name` | `code` is the stable handle for colors and content paths. |
| `units` | `id`, `subject_id`, `grade`, `title`, `position` | |
| `lessons` | `id`, `unit_id`, `title`, `kind` (lesson, practice, game, sim), `position`, `status` | |
| `questions` | `id`, `lesson_id`, `type`, `prompt`, `body` (json), `answer` (json), `explanation`, `difficulty`, `skill_code`, `status`, `version` | Published questions are never edited in place when the meaning changes (8). |
| `assignments` | `id`, `class_id`, `lesson_id`, `assigned_by`, `due_at` | |
| `attempts` | `id`, `student_id`, `lesson_id`, `mode` (practice, test), `started_at`, `finished_at`, `score`, `max_score` | One row per try. Never overwritten. |
| `attempt_answers` | `id`, `attempt_id`, `question_id`, `response` (json), `is_correct`, `time_ms` | Lets the product say what to review, and lets a teacher see the most-missed question. |
| `lesson_progress` | `student_id`, `lesson_id`, `status`, `best_score`, `last_activity_at` | A cache derived from `attempts`; rebuildable. |
| `activity_days` | `student_id`, `day` | Streaks are computed from this, not stored as a counter. |
| `game_sessions` | `id`, `student_id`, `lesson_id`, `score`, `level_reached`, `data` (json), `ended_at` | |
| `sim_saves` | `id`, `student_id`, `lesson_id`, `params` (json), `created_at` | The parameter object of a simulation. |

In a document database the same model becomes: `users/{uid}` · `classes/{classId}` with `members/{uid}` · `lessons/{lessonId}` with `questions/{questionId}` · `users/{uid}/attempts/{attemptId}` · `users/{uid}/progress/{lessonId}`.

### 7.8 Migrations: expand, migrate, contract
One change per migration. Name files `YYYYMMDDHHMM_<verb>_<object>.sql`. Never edit a migration that has been applied. Seed data is separate from migrations. A safe rename looks like this:

```sql
-- 1. expand: add the new column, keep the old one
ALTER TABLE profiles ADD COLUMN display_name text;

-- 2. migrate: copy the data; during the transition the app writes both columns
UPDATE profiles SET display_name = ten WHERE display_name IS NULL;

-- 3. switch the app to read display_name, deploy, verify (7.9)

-- 4. contract: a later migration, only after verification and the user's yes
ALTER TABLE profiles ALTER COLUMN display_name SET NOT NULL;
ALTER TABLE profiles DROP COLUMN ten;
```

### 7.9 Verification queries
Run them before and after, and compare.

```sql
-- row counts must match what the plan predicts
SELECT COUNT(*) FROM attempts;

-- orphans: answers whose attempt no longer exists
SELECT a.id FROM attempt_answers a LEFT JOIN attempts t ON t.id = a.attempt_id WHERE t.id IS NULL;

-- duplicates: one student enrolled twice in the same class
SELECT class_id, student_id, COUNT(*) FROM enrollments GROUP BY class_id, student_id HAVING COUNT(*) > 1;

-- a column that should hold a fixed set of values
SELECT status, COUNT(*) FROM lessons GROUP BY status ORDER BY 2 DESC;
```

### 7.10 Privacy: the users are minors
Store the minimum (`SKILL.md` E10). Keep identity (name, class) apart from learning events where feasible. No passwords in your own tables: use the auth provider. No personal data in logs or analytics. Deleting an account removes or anonymizes its data. Access by role is enforced **in the database** (row-level security or rules), not only in the interface. Where the law requires a guardian's consent for children's data, flag it for the team to verify; do not guess the legal detail.

## 8. Content data (lessons, questions, items)

**Shape.** Every item has a stable `id`, a `type`, a `version`, a `status`, where it belongs (subject, grade, unit, lesson), and for questions a `prompt`, `options` that each carry their own id, an `answer` that refers to **option ids** (one id for single choice, a list of ids for multiple choice; never positions or text, so shuffling and editing cannot break it), an `explanation`, an optional `hint`, and media references with alt text.

```json
{
  "id": "math-6-gcd-01",
  "type": "single-choice",
  "version": 1,
  "status": "published",
  "subject": "math", "grade": 6, "lesson": "ucln",
  "skill": "gcd", "difficulty": 1,
  "prompt": "ƯCLN(12, 18) bằng bao nhiêu?",
  "options": [
    { "id": "a", "text": "2" },
    { "id": "b", "text": "3" },
    { "id": "c", "text": "6" },
    { "id": "d", "text": "9" }
  ],
  "answer": "c",
  "explanation": "Các ước chung của 12 và 18 là 1, 2, 3, 6. Số lớn nhất trong đó là 6.",
  "reviewedBy": null
}
```

**Rules.**
- Ids are never reused or changed after publishing: attempts point at them. An edit that changes a question's meaning creates a new version.
- Text is NFC. Notation follows `SKILL.md` E8. No raw HTML in content strings: use plain text, or a small structured format the renderer controls.
- An answer key is not trusted until a teacher has reviewed it; `reviewedBy` stays empty until then, and the interface or the report says so.
- File-based content lives at `content/<subject>/grade-<n>/<lesson>.json`. One file per lesson, not one giant file.

**Validation before content ships** (a small script, or checks at the write boundary): ids unique · every `answer` names an existing option · 2-5 options · every question has an explanation · no empty strings · referenced media exists · subject and skill codes come from the fixed list.

**Cleaning existing content:** duplicates (the same normalized prompt), near-duplicates, broken references, missing explanations, inconsistent subject codes, stray spaces, mixed encodings, answers stored as positions or as text.
